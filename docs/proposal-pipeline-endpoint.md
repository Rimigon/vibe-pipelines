# Предложение: `POST /generate/pipeline` — server-side генеративные пайплайны

**Статус:** предложение для платформы Вайб-Маркетолог.
**Референс-реализация сегодня:** `vibe-pipelines` (этот репозиторий) —
клиентский оркестратор, доказывающий UX и спрос.

## Проблема

Agent API даёт универсальный `/generate` (один шаг генерации) и сопутствующие
`/upload-media`, `/generate/estimate`, webhooks, polling. Но реальный
маркетинговый сценарий — это **DAG из нескольких генераций**:

```
постер (image) ──┐
                 ├──> видео (image-to-video, eats poster) ──> ролик
джингл (music) ──┘                                         + наложение музыки
озвучка (voice) ─────────────────────────────────────────────┘
```

Сегодня агент собирает это вручную: запустить шаг A → поллить/ждать вебхук →
забрать `display_url` (живёт 7 дней) → подставить в шаг B → повторить. Каждый
шаг — отдельный round-trip, отдельный поллинг, отдельная обработка ошибок и
refunds. Промежуточный файл может протухнуть, пока зависимый шаг не успел его
скачать. Бюджет сценария приходится считать самому. Ошибка в имени поля
(`image_input` для видео) молча превращает image-to-video в text-to-video и
**списывает деньги**.

Всё это — рутина, которую повторяет каждый разработчик агента. Это ровно то,
что вакансия называет «строить устойчивые генеративные пайплайны: маршрутизация
моделей, fallback, retries, очереди, webhooks, лимиты, контроль стоимости,
обработка ошибок» — но сегодня она лежит на клиенте.

## Предложение

`POST /generate/pipeline` — атомарный запуск мультимодельного сценария на
стороне платформы:

```json
POST /api/agent/pipeline
Authorization: Bearer oc_...
{
  "budget_rub": 480,
  "idempotency_key": "camp_42",
  "callback_url": "https://my.host/pipeline-webhook",
  "steps": [
    {"id": "poster", "type": "image", "model": "seedream-5-pro",
     "prompt": "баннер салона красоты", "params": {"aspect_ratio": "1:1"}},
    {"id": "jingle", "type": "music", "model": "suno-v5.5-instrumental",
     "prompt": "upbeat pop-джингл, 15 сек"},
    {"id": "clip", "type": "video", "model": "seedance-2-mini",
     "prompt": "зум на баннер",
     "inputs": {"source_image": {"from_step": "poster"}},
     "after": ["poster"],
     "params": {"duration": 4, "aspect_ratio": "9:16", "resolution": "480p"}}
  ]
}
```

**Ответ:**

```json
{
  "status": "processing",
  "pipeline_id": 9001,
  "estimated_cost_rub": 195,
  "balance_after": 305,
  "status_url": "/api/agent/pipeline/9001"
}
```

### Что платформа делает сама

1. **Валидация и смета до списания.** Каждый шаг прогоняется через существующий
   `/generate/estimate`-движок; если сумма > `budget_rub` — `402/422` с
   per-step breakdown, ни одной генерации не запускается.
2. **Маппинг полей.** Логические входы (`source_image`, `source_audio`,
   `source_video`) маппятся на физические поля по схеме из `/capabilities`
   (решает `image_input`-footgun централизованно, для всех агентов сразу).
3. **Очередь + DAG.** Шаги исполняются в топо-порядке; независимые — параллельно.
   Промежуточные файлы живут **во внутреннем хранилище** (не публичный
   `display_url` с TTL 7 дней) → не протухают.
4. **Fallback моделей.** При retryable-сбое шага платформа перепробует резервную
   модель того же тира (расширяет существующий внутренний multi-engine reserve
   на уровень сценария).
5. **Атомарный бюджет и refunds.** Один `idempotency_key` на весь сценарий;
   `cost`/`refunded` агрегируются по шагам; при превышении `budget_rub` в
   процессе — остановка оставшихся шагов.
6. **Один вебхук по завершению.** `pipeline.complete` / `pipeline.error` с
   результатами всех шагов — вместо N вебхуков клиенту.

### `GET /api/agent/pipeline/{id}`

```json
{
  "status": "complete",
  "pipeline_id": 9001,
  "steps": {
    "poster": {"status": "complete", "display_url": "https://.../9001/poster?sig=..", "cost": 40},
    "jingle": {"status": "complete", "display_url": "https://.../9001/jingle?sig=..", "cost": 99},
    "clip":   {"status": "complete", "display_url": "https://.../9001/clip?sig=..",   "cost": 56}
  },
  "cost": 195, "refunded": 0, "net_cost": 195
}
```

## Почему это ценно для платформы

- **Снижает порог входа.** Сегодня «собрать рекламный ролик из 4 генераций» —
  задача на сотни строк клиента. С `/pipeline` — один декларативный запрос. Это
  делает API доступным не только для разработчиков агентов, но и для
  нетехнических маркетологов через YAML/конструктор (как `vibe run reel.yaml`).
- **Увеличивает средний чек сценария.** Платформа получает «заказ целиком», а не
  отдельные генерации — проще продавать пакетами и считать unit-экономику
  сценария.
- **Закрывает footgun на корне.** Маппинг полей в одном месте = ни один агент
  больше не платит за `image_input`-в-видео. Это прямая экономия рекламного
  бюджета клиентов и снижение обращений в поддержку.
- **Естественная основа для AGI-агентов.** `agi.vibemarketolog.ru` ставит задачу
  и лимит — `/pipeline` исполняет её атомарно, с трассировкой и восстановлением.
  Это и есть «автономные действия 24/7» на уровне платформы, а не каждого агента.

## Что уже доказывает референс-реализация (`vibe-pipelines`)

- **UX работает сегодня.** Декларативный DAG, логические входы, бюджетный шлюз,
  resume, вебхуки — всё поверх существующего API, 38 тестов на моках из доки.
- **Спрос подтверждён паттерном.** Вся «боль» (footgun, протухание URL, ручной
  поллинг, ручной подсчёт сметы) задокументирована в самом API — значит, платформа
  уже видит эти ошибки у пользователей.
- **Маппинг полей уже реализован** (`vibe/capabilities.py`) — его можно
  перенести на бэкенд один-в-один.

## Migration / совместимость

`/pipeline` — **новый** эндпоинт, не ломает существующий `/generate`. Скоуп
OAuth — новый `pipeline` (или переиспользовать `generate`). Старые агенты
работают как прежде; новые получают атомарный сценарий. Клиентская библиотека
остаётся актуальной для тех, кому нужен полный контроль (low-level).

## Открытые вопросы

- Нужен ли `pipeline_id` в журнале/галерее ЛК (как `generation_id` сегодня)?
- Показывать ли прогресс шагов в реальном времени (SSE) или достаточно поллинга
  - вебхука?
- Допускать ли `model: "auto"` + `tier` на уровне шага (агентский router) или
  держать явный выбор модели?
